### Q1. TCP 3-way handshake 과정을 순서대로 설명해주세요.

```text
클라이언트                 서버

    │                       │
    │──────── SYN ─────────→│  ① 연결 요청
    │←────── SYN+ACK ───────│  ② 요청 수락
    │──────── ACK ─────────→│  ③ 연결 확립
```

- `SYN`: "연결 시작해도 될까요?"
- `SYN+ACK`: "요청 받았고, 나도 연결 준비됐어요."
- `ACK`: "확인했어요. 이제 데이터 통신 시작합시다."

#### 왜 2번이 아니라 3번일까?

핵심은 **양쪽 모두의 송수신 가능 상태를 확인**해야 하기 때문이다.

- 2-way만 하면 서버 입장에서는 클라이언트가 마지막 응답을 받았는지 확신할 수 없다.
- 3번째 `ACK`를 받아야 서버도 "클라이언트가 내 응답을 정상 수신했구나"를 확정한다.
- 이 과정을 통해 오래된 지연 패킷으로 생길 수 있는 잘못된 연결 문제를 줄일 수 있다.

그래서 **3-way가 필요**하다.

**마지막 ACK의 의미**

`클라이언트가 서버 응답을 "진짜로" 받았다는 증거`

🔥 **핵심 포인트**

서버 입장에서  
`내 SYN+ACK가 제대로 전달됐는지 확인해야 함`

👉 그걸 확인해주는 게 3번째 `ACK`

#### 문제 상황 (유령 연결)

클라이언트 → 서버:

- `SYN` 보냄 (근데 네트워크 지연됨)
- 서버는 나중에 그걸 받고: "어? 연결 요청 왔네" → 연결 생성
- 근데 클라이언트는 이미 포기한 상태일 수도 있음

💥 결과

- 서버는 연결 열림
- 클라이언트는 모름
- 즉, **유령 연결(half-open connection)** 발생

💡 **한 줄 정리 (면접용)**

> 3-way handshake는 단순 연결 요청/응답이 아니라, 양쪽 모두가 서로의 송수신 가능 상태를 확인하기 위해 필요합니다.  
> 특히 마지막 ACK는 서버가 보낸 SYN+ACK가 정상적으로 전달되었음을 보장하여 half-open connection을 방지합니다.

#### 👉 4-way handshake는 왜 4번이냐? (세트 질문)

연결 종료 흐름은 이렇게 간다:

- 클라이언트 → 서버: `FIN`
- 서버 → 클라이언트: `ACK`
- 서버 → 클라이언트: `FIN`
- 클라이언트 → 서버: `ACK`

🧠 **단계별 의미**

**① FIN (클라이언트 → 서버)**  
클라이언트: "내가 보낼 데이터는 끝났어. 종료할게."

**② ACK (서버 → 클라이언트)**  
서버: "FIN 확인했어."  
단, 이 시점에는 서버가 보낼 데이터가 아직 남아있을 수 있다.

**③ FIN (서버 → 클라이언트)**  
서버: "나도 전송 끝났어. 이제 종료할게."

**④ ACK (클라이언트 → 서버)**  
클라이언트: "FIN 확인. 연결 완전히 종료."

🔥 **그럼 왜 4번이냐 (핵심 질문)**

핵심 차이: **종료는 양방향이 따로 진행됨**

- 연결(3-way): 동시에 연결 시작 확인이 가능해서 일부를 묶어 처리 가능
- 종료(4-way): 한쪽이 먼저 끊어도 반대쪽은 보낼 게 남아있을 수 있음

그래서 `FIN + ACK`를 한 번에 못 묶고, 각자 따로 보내야 한다.

📌 **핵심 포인트**

- 연결은 "같이 시작" 가능
- 종료는 "각자 끝내야 함"

💡 **한 줄 정리 (면접용)**

> TCP 연결 종료는 양방향 통신이 독립적으로 종료되기 때문에 각 방향마다 FIN과 ACK가 필요하여 총 4-way handshake가 발생합니다.

🚀 **추가로 말하면 좋은 포인트 (플러스 점수)**

**TIME_WAIT**
- 마지막 ACK를 보낸 쪽이 잠시 기다리는 상태
- 이유 1: 마지막 ACK 유실 대비
- 이유 2: 네트워크에 남아 있는 지연 패킷 정리

🔥 **3-way vs 4-way 한 방 정리**

| 구분 | 이유 |
| --- | --- |
| 3-way | 서로 연결 가능 확인 |
| 4-way | 각자 따로 연결 종료 |

**진짜 핵심 요약**
- 3-way: "서로 연결 가능?"
- 4-way: "각자 다 끝났어?"

### Q2. 온라인 쇼핑몰에서 동시 접속자 100만 명의 세션을 관리해야 합니다. 어떤 자료구조를 쓰시겠어요?

이 상황에서는 **해시 테이블**이 가장 적합하다.

이유:

- 세션은 보통 `sessionId -> sessionData` 형태의 키-값 조회가 중심이다.
- 해시 테이블은 키 기반 조회/삽입/삭제가 평균 `O(1)`이라 대규모 동시 처리에 유리하다.
- Redis 같은 인메모리 저장소도 내부적으로 해시 기반 접근을 적극 활용한다.

❌ **다른 선택지는 왜 탈락인지**

**A) 배열**
- "`O(1)`이라서"라고 고르면 함정이다.
- `userId`는 보통 1,2,3 같은 연속값이 아니라 UUID/랜덤값인 경우가 많다.
- 그래서 배열 인덱스로 바로 쓰기 어렵고, 메모리 낭비가 크거나 사실상 불가능하다.

**C) 이진 탐색 트리**
- 조회가 `O(log N)`이라 해시보다 느리다.
- 세션 저장은 정렬보다 즉시 조회가 더 중요하다.

**D) 연결 리스트**
- 조회가 `O(N)`이라 사용자 수가 늘수록 급격히 느려진다.
- 동시 접속자 100만 명 상황에서는 선형 탐색 비용이 너무 크다.

🔥 **한 단계 더 (면접 플러스 점수 포인트)**

**1) 분산 환경**
- 실제 서비스는 단일 서버보다 여러 서버로 구성되는 경우가 많다.
- 그래서 Redis 같은 인메모리 저장소에 세션을 두고 공유/분산 처리한다.

**2) TTL(세션 만료)**
- 세션은 자동 만료 정책이 필수다.
- 해시 구조 + 만료 시간 정책을 같이 설계해야 한다.

**3) 충돌 처리**
- 해시 충돌은 반드시 고려해야 한다.
- 체이닝(Chaining) 또는 오픈 어드레싱(Open Addressing) 같은 전략이 필요하다.

💡 **한 줄 면접 답변**

> 세션은 userId 기반으로 빠르게 조회되어야 하고 키가 비연속적이기 때문에, 평균 O(1) 조회가 가능한 해시 테이블이 적합합니다.  
> 배열은 인덱스 기반이라 부적합하고, 트리는 정렬이 필요 없는 세션 조회에서는 오버헤드가 큽니다.

📌 **핵심 포인트**

자료구조는 시간복잡도 숫자만 보는 게 아니라, **데이터 형태와 접근 패턴**을 먼저 봐야 한다.

### Q3. DB 인덱스는 왜 B-Tree를 쓸까요? 해시 테이블이 O(1)인데 더 빠르지 않나요?

핵심 답변: **범위 검색(Range Query)** 때문이다.

- B-Tree는 정렬된 상태를 유지해서 `<`, `>`, `BETWEEN`, `ORDER BY`, prefix 검색에 유리하다.
- 해시 인덱스는 등호(`=`) 검색은 빠르지만 범위 검색이 사실상 어렵다.
- DB는 단건 조회만 하는 게 아니라 정렬/범위 조건이 매우 자주 나오므로 B-Tree가 범용적으로 쓰인다.

✅ **B-Tree를 쓰는 핵심 이유 3가지**

**1) 정렬된 구조**
- 항상 오름차순 정렬 상태를 유지한다.
- 그래서 범위 조회와 `ORDER BY` 처리에 유리하다.

**2) 범위 조회에 강함**
- 예: `WHERE price > 10000`
- 특정 지점부터 리프 노드를 연속 탐색할 수 있다.

**3) 디스크 I/O 최적화 (진짜 핵심)**
- B-Tree는 한 노드에 많은 키를 저장한다.
- 트리 높이가 낮아져서 루트~리프 탐색 단계가 줄어든다.
- 결과적으로 디스크 접근 횟수를 최소화할 수 있다.

#### 그럼 해시 인덱스는 언제 쓰나요?

- 완전 일치(Exact Match) 조회가 압도적으로 많은 경우
- 범위/정렬 조건이 거의 없는 경우
- 키 충돌 관리와 메모리 사용량 trade-off를 감수할 수 있는 경우

즉, 해시 인덱스는 "특정한 패턴에 최적화된 특수 카드",  
B-Tree는 "대부분 상황에서 안정적인 기본 카드"에 가깝다.

#### 시간복잡도 비교 (함정 포인트)

| 구조 | 조회 |
| --- | --- |
| 해시 | O(1) |
| B-Tree | O(log N) |

👉 근데 DB에서는 **시간복잡도 숫자보다 디스크 I/O 횟수**가 더 중요하다.

💡 **한 줄 핵심**

> 메모리에서는 O(1)이 중요하지만, 디스크에서는 접근 횟수가 더 중요하다.

🚀 **면접용 완성 답변**

> 해시 테이블은 단건 조회는 빠르지만 정렬과 범위 조회를 지원하지 못하고, 랜덤 디스크 접근이 많아 DB 인덱스로는 부적합합니다.  
> 반면 B-Tree는 정렬된 구조를 유지하여 범위 조회와 ORDER BY에 유리하고, 트리 높이를 낮춰 디스크 I/O를 최소화할 수 있기 때문에 인덱스로 사용됩니다.

🔥 **한 방 정리**

- 해시 = 빠른 단건 조회
- B-Tree = DB에 필요한 기능(범위 + 정렬 + I/O 최적화)

### 한 줄 요약

기술 면접 단골 3문제의 핵심은 이것이다:  
**TCP는 연결 신뢰성, 세션은 해시 기반 즉시 조회, DB 인덱스는 범위 검색 때문에 B-Tree.**
